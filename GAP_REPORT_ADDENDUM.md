# Gap Report Addendum — verified against live Google Ads API docs (2026-09-09)

`GAP_REPORT.md` is generated by `coverage_scan.py`, which diffs the connector code
against a stored per-source capability list (`_reference/<source>.json`). That's why
its "missing" rows are all *fields on resources we already query* (segments, metrics).
It cannot surface **whole resources the connector never queries at all** — those were
never in the reference list to begin with. Cross-checking the report-name list in your
screenshot (a Google Ads UI export folder) against current API docs turns up six such
resources. None of these appear anywhere in `GAP_REPORT.md` or `EXTRACTION_INVENTORY.md`.

## New gaps (verified, not in GAP_REPORT.md)

**1. `landing_page_view` / `expanded_landing_page_view` — Landing page report**
Aggregates cost/clicks/conversions by unexpanded and expanded final URL. Confirmed live in the v22 field reference. Nothing in the current entity or performance stream list queries it — `ad_performance` has `ad.final_urls` at the ad level but not this aggregated view, and campaign/ad-group rollups can't answer "which landing page converts."

**2. `user_location_view` — Matched locations report**
The connector's `geo_performance` stream queries `geographic_view`, which Google Ads Help confirms maps to the **"Targeted locations"** UI view. The distinct **"Matched locations"** UI view — physical or interest-based location, which can differ from what was targeted — comes from `user_location_view`, distinguished by its `targeting_location` field. Same base metrics as `geographic_view`, so this is a one-stream addition, not new plumbing.

**3. `ad_schedule_view` — Ad schedule / Ad schedule day-and-hour reports**
This is a distinct resource, joined against `campaign_criterion.ad_schedule` (day_of_week, start_hour, end_hour) to reproduce the UI's Ad Schedule report. Nothing in the connector queries `campaign_criterion` at all currently. Worth noting from research: `ad_schedule_view` itself doesn't support an hour-level segment — Google's own forum confirms `segments.hour` isn't selectable there — so the "day and hour" breakdown has to be built from the criterion's stored `start_hour`/`end_hour` fields, not a query segment. `segments.hour` (as a general date-part segment on other resources) is separately absent from `GAP_REPORT.md`'s google_analytics list of missing dimensions too — GA4 has `hour` as a dimension and it isn't pulled by any GA4 stream either.

**4. `dynamic_search_ads_search_term_view` — Dynamic ad target report**
Confirmed live in the v21/v22 field reference: `search_term`, `landing_page`, `headline`, `page_url`, plus the base metrics, segmentable by date/day-of-week/conversion action. No DSA-specific stream exists in the connector at all — regular `search_term_performance` (from `search_term_view`) won't carry DSA's landing-page/headline attribution.

**5. Content targeting resources — Targeted content report**
Google Ads splits "Content" targeting reporting across `topic_view`, `managed_placement_view`, `group_placement_view`, and `detail_placement_view` (per a Google Ads API forum thread distinguishing managed vs. automatic placements). None are in the connector. Only relevant for accounts running Display/Video campaigns with topic or placement targeting — worth checking whether Curelo/HireIQ ad accounts actually use Display before prioritizing this one.

**6. `campaign_criterion.bid_modifier` / `ad_group_criterion.bid_modifier` — Advanced bid adjustment report**
Bid modifiers (device, ad schedule via `InteractionTypeInfo.CALL`, and others) live on `campaign_criterion` and `ad_group_criterion`, confirmed in the current `CampaignCriterion` RPC reference. The connector doesn't query either resource for bid-modifier fields today; `campaign_device_performance` shows device *performance* but not the *bid adjustment* set for that device.

## Platform ceiling, not a code gap

**Auction insights report** — confirmed across multiple 2026 sources (Google Ads API forum threads and third-party guides updated this year) that Auction Insights metrics (`auction_insight_search_impression_share`, `_outranking_share`, `_overlap_rate`, etc.) are **still not exposed via the Google Ads API** as of 2026, despite a long-standing feature request. Looker Studio's connector for it was also cut off in August 2024. The only way to get this data today is a scheduled UI/email export into Sheets — there's no API path to automate it, so this shouldn't be tracked as a connector gap at all, just a documented limitation.

## Implementation specs — ready to drop into `_PERF_STREAMS`/entity streams

Format matches `EXTRACTION_INVENTORY.md`'s existing stream tables. Fields confirmed against the live v22 field reference; a couple of items are flagged where you should re-verify field names against your account's exact API version before shipping.

### 1. `landing_pages` (new entity/performance stream)

| Field | Value |
|---|---|
| Resource | `landing_page_view` (unexpanded) and `expanded_landing_page_view` (expanded) — two separate queries, same shape |
| Segmenting resources | `campaign`, `ad_group` — join these in if you want landing page broken out by campaign/ad group, not just account-wide |
| Dimensions | `segments.date`, `landing_page_view.unexpanded_final_url` (or `expanded_landing_page_view.expanded_final_url`) |
| Metrics | Same `_BASE_METRICS` set you already use elsewhere — `impressions`, `clicks`, `cost_micros`, `conversions`, `conversions_value`, `all_conversions`, `ctr`, `average_cpc` all confirmed selectable on this resource |
| Note | Community reports (Google Ads API forum) flag totals from this view sometimes not reconciling exactly with account-level totals — expect ~single-digit % variance, not a bug in your code |

```sql
SELECT segments.date, campaign.id, campaign.name, landing_page_view.unexpanded_final_url,
       metrics.impressions, metrics.clicks, metrics.cost_micros, metrics.conversions,
       metrics.conversions_value, metrics.ctr, metrics.average_cpc
FROM landing_page_view
WHERE segments.date DURING LAST_30_DAYS
```

### 2. `user_location_performance` (new performance stream, sibling to your existing `geo_performance`)

| Field | Value |
|---|---|
| Resource | `user_location_view` |
| Dimensions | `campaign.id`, `user_location_view.country_criterion_id`, `user_location_view.targeting_location` (bool — this is the field that distinguishes matched vs. targeted) |
| Metrics | Same `base` set as `geo_performance` |
| Note | Same shape as your existing `geo_performance` stream — can likely reuse most of that stream's code, swapping the resource name and adding `targeting_location` |

### 3. `ad_schedule` (new entity stream — not a performance/fact stream)

| Field | Value |
|---|---|
| Resource for criteria | `campaign_criterion` filtered `WHERE campaign_criterion.type = 'AD_SCHEDULE'` |
| Fields | `campaign.id`, `campaign_criterion.criterion_id`, `campaign_criterion.ad_schedule.day_of_week`, `.start_hour`, `.start_minute`, `.end_hour`, `.end_minute`, `campaign_criterion.status` |
| Resource for performance | `ad_schedule_view`, joined conceptually to the criteria above via `campaign_id~criterion_id` |
| Note (confirmed via forum) | `ad_schedule_view` does **not** support `segments.hour` — you cannot get an hour-level performance segment from it directly. To reproduce the UI's "day and hour" grid, pull `campaign_criterion.ad_schedule` (which already encodes start/end hour per schedule block) and match it against `segments.day_of_week` performance from `campaign_performance` — don't expect a single query to return this cleanly |

### 4. `dynamic_search_ads_search_terms` (new performance stream)

| Field | Value |
|---|---|
| Resource | `dynamic_search_ads_search_term_view` |
| Attributed (non-segmenting) resources | `ad_group`, `campaign`, `customer` |
| Dimensions | `segments.date`, `dynamic_search_ads_search_term_view.search_term`, `.landing_page`, `.headline`, `.page_url` |
| Also useful | `.has_negative_keyword`, `.has_negative_url`, `.has_matching_keyword` (booleans, good for exclusion-candidate flagging) |
| Metrics | `clicks`, `impressions`, `cost_micros`, `client_account_conversions`, `client_account_conversions_value`, `ctr`, `average_cpc` — note the field names on this view are `client_account_conversions*`, not the plain `conversions` your other streams use; confirm this in your account's exact API version before wiring it into `_BASE_METRICS` handling |

### 5. Bid modifiers (new entity stream)

| Field | Value |
|---|---|
| Resource | `campaign_criterion` (device, ad schedule via `interaction_type = CALL`) and `ad_group_criterion` (device, Hotel Ads criteria) |
| Fields | `campaign.id`, `campaign_criterion.bid_modifier`, `campaign_criterion.device.type`, `campaign_criterion.criterion_id` — same shape for `ad_group_criterion` |
| Note | This is a criterion/config pull, not a daily fact — treat it like your `conversion_actions` entity stream (snapshot, not time series) |

### 6. Content targeting — hold off pending a usage check

`topic_view`, `managed_placement_view`, `group_placement_view`, `detail_placement_view` are the four resources involved, but I haven't pulled their exact field lists here — worth doing before implementing, since this only matters if the ad accounts actually run Display/Video campaigns with topic or placement targeting (Search-only accounts won't have any data here). Flagging as lowest priority of the six pending that check.

## Net effect on the google_ads coverage number

`GAP_REPORT.md` shows google_ads at 73% against its stored reference surface. The six items above are resources outside that reference surface entirely (the scan can't diff what it was never told to look for), so the *true* gap against "everything the Google Ads UI can report" is larger than 73% suggests. Recommend adding `landing_page_view`, `user_location_view`, `ad_schedule_view` + `campaign_criterion`, `dynamic_search_ads_search_term_view`, and the placement/topic views to `_reference/google_ads.json` so future scans catch resource-level gaps like this automatically, not just field-level ones on existing streams.
