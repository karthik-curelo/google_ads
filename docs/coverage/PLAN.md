# API Coverage Audit — Plan

**Goal:** answer, with evidence, "are we collecting everything each source API can
give us?" — and keep answering it as the APIs change.

## 1. What "complete" means

Every relevant API resource × every supported dimension / metric / breakdown ×
full available history, **minus** documented platform limits. Four hard ceilings
we never claim past:

| Source | Ceiling |
|---|---|
| GSC | Search Analytics returns *top* rows under an internal cap, not every row |
| GA4 | Data API samples / thresholds; row-level truth is BigQuery Export |
| Google Ads | Field compatibility — not every metric works with every resource/segment |
| Meta | Metric + breakdown availability varies by version, object, and access tier |

The manifest records `status: platform_limited` for these instead of pretending 100%.

## 2. Deliverable — the coverage manifest

`docs/coverage/<source>.yaml`, one per source, machine-readable, checked in.
Generated by `scripts/coverage_scan.py`. Schema:

```yaml
source: google_ads
api_version: v25
generated: 2026-09-07
resources:
  campaign:            { status: implemented, stream: campaigns }
  search_term_view:    { status: implemented, stream: search_term_performance }
metrics:
  metrics.impressions:      implemented
  metrics.all_conversions:  implemented
segments:
  segments.device:  implemented
breakdowns: n/a
history:  { supported_days: unlimited, implemented: backfill_days_setting }
verified_in_db: false   # flipped true by the Phase D test
```

`status` ∈ `implemented | partial | missing | unsupported | permission_gated | platform_limited`.

## 3. Phases

### Phase A — reference inventory (what the API *could* give)
`docs/coverage/_reference/<source>.json` — the authoritative capability list.

- **GA4** — refreshable from `GET {DATA_BASE}/properties/{id}/metadata` (already
  called in `analytics.py` `get_schema`). Plus the fixed report methods.
- **Google Ads** — refreshable from `GoogleAdsFieldService`
  (`SELECT name, category, selectable, selectable_with FROM google_ads_field`).
- **GSC / Meta / Instagram** — hand-maintained from the API reference, version
  stamped, with a `review_by` date.

### Phase B — current coverage from code (what we *do* get)
`scripts/coverage_scan.py` imports the registry and reads the declarative stream
dicts (`_REPORTS`, `_DIMENSIONS`, `_ENTITY_STREAMS`/`_PERF_STREAMS`,
`_ENTITY_EDGES`/`_INSIGHT_FIELDS`, connector `STREAMS`).

### Phase C — diff → gap report
`scripts/coverage_scan.py --write` joins A against B, fills `status`, writes the
per-source YAML and `docs/coverage/GAP_REPORT.md`.

### Phase D — prove each stream reaches the database
One parametrised Postgres test: bounded sync per stream → assert rows in
`report_rows` / `ad_entities` → set `verified_in_db: true`. Google connectors run
against the live connections today; Meta/IG stay `permission_gated` until access
lands.

### Phase E — keep it honest
Weekly CI job: re-run Phase A for GA4 + Google Ads (the two with metadata APIs),
diff against the committed `_reference/*.json`, fail if the API grew capabilities
the manifest doesn't mention. GSC/Meta get a dated review line, no automation.

## 4. Order of attack

1. Phases A–C for all six sources → manifest + gap report.
2. Phase D harness → flips `verified_in_db`.
3. Then close gaps, `value: high` first. The connectors are declarative, so each
   gap is a dict entry, not a rewrite.
